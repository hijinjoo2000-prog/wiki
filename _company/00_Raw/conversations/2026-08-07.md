수익화 가설(인지 부하 감소와 결제율의 관계)과 A/B 테스트 프레임워크를 기반으로, '공인중개사 결제 100건' 목표 달성에 가장 직접적으로 기여하는 **최우선 실행 단계**를 다음과 같이 확정합니다.

### 1. 최종 MVP 정의 (Minimum Viable Product)

가장 높은 가치(인지 부하 감소)를 측정하고, 최소한의 마찰로 전환을 유도하기 위해 다음의 구체적인 MVP를 정의합니다.

**MVP 목표:** 공인중개사가 '정보 입력' 단계를 최소화하여 서비스 이용에 대한 심리적 장벽(인지 부하)을 획기적으로 낮추고, 그 결과로 결제율을 최대화한다.

**핵심 기능 (Must-Have):**
1. **초단순 정보 입력 모듈:** 복잡한 설문이나 다단계 입력을 배제하고, 핵심 가치(예: 부동산 정보의 효율성)를 3~5개의 필수 항목으로 압축하여 즉시 입력할 수 있는 UI/UX 구현. (Designer가 제시한 '최소 마찰 조건(B 그룹)'에 집중)
2. **즉각적인 피드백 루프:** 사용자가 정보를 입력하는 즉시, 시스템이 해당 정보의 가치(인지 부하 감소 효과)를 시각적으로 제공하여 다음 단계로 넘어가도록 유도하는 명확한 인센티브 제시. (MrBeast 후킹 로직 적용)
3. **단일 결제 경로:** MVP 테스트 기간 동안은 복잡한 번들 옵션 대신, 가장 단순하고 직접적인 가격 구조(예: 고정 수수료 또는 단일 프리미엄 패키지)를 설정하여 전환율 측정에 집중.

**MVP 제외 항목 (Nice-to-Have / Future Scope):**
*   복잡한 개인화 설정 기능.
*   다중 구독 모델의 복잡한 관리 기능.
*   광범위한 지역별 상세 분석 리포트 제공 (초기에는 전환율 측정에 집중).

### 2. 핵심 KPI 측정 기준 (Key Performance Indicators)

MVP가 가설을 검증하고 매출화로 이어지는지 측정하기 위해, 인지 부하 감소와 결제율의 관계를 정량적으로 입증하는 지표를 설정합니다.

| :--- | :--- | :--- | :--- | :--- |
| **인지 부하 측정** | **TTC (Task Completion Time)** | 입력 완료 시간 단축 | 사용자 세션 기록 (입력 시작부터 완료까지) | 인지 부하 감소가 실시간으로 반영되는지를 측정. 시간이 짧을수록 성공적인 '저마찰' 디자인임을 증명. |
| **전환율 측정** | **PCR (Purchase Conversion Rate)** | MVP 테스트 그룹의 결제 전환율 | A/B 테스트 그룹별 결제 발생률 | 최종 목표인 '결제 100건' 달성의 직접적 지표. 인지 부하가 낮을 때의 자연스러운 구매 의향을 측정. |

## 📊 A/B 테스트 프레임워크 및 핵심 KPI 최종 확정 보고

### 1. 연구 목표 (Hypothesis)

**가설:** 사용자 경험 내의 **인지 부하 감소**는 사용자의 정보 처리 마찰(TTC, PCR)을 줄여, 궁극적으로 **실제 결제율(Conversion Rate)**을 정량적으로 향상시킨다.

### 2. 핵심 측정 지표 (Key Performance Indicators, KPIs) 정의

A/B 테스트의 성공 여부를 판단하기 위해 세 가지 레벨의 지표를 설정합니다.

| 구분 | 지표명 | 정의 | 측정 대상 | 목표 연결성 |
| :--- | :--- | :--- | :--- | :--- |
| **독립 변수 (Input)** | **TTC (Task Completion Time)** | 사용자가 특정 작업을 완료하는 데 걸리는 시간. (인지 부하의 직접적 지표) | 사용자 경험 (UX/UI 설계 변경) | 인지 부하 감소 측정 |
| **독립 변수 (Input)** | **PCR (Perceived Cognitive Load)** | 사용자가 인지적으로 느끼는 작업의 복잡성 또는 어려움의 주관적 평가. (사용자 피드백 기반) | 사용자 경험 (UX/UI 설계 변경) | 인지 부하 감소 측정 |
| **종속 변수 (Output)** | **Conversion Rate (CR)** | 특정 행동(예: 결제 완료)으로 이어진 사용자의 비율. | 비즈니스 성과 | 최종 목표 달성 측정 |

### 3. A/B 테스트 프레임워크 설계 (The Efficiency Framework)

가장 효율적인 테스트는 '인지 부하'라는 추상적 개념을 구체적인 행동 지표(TTC, PCR)와 실제 결과(CR)로 연결하는 것입니다.

**프레임워크 명칭:** **Friction-to-Revenue Correlation Test (FTRC)**

#### 단계 1: 실험 그룹 정의 (Segmentation)
*   **그룹 A (Control):** 기존의 복잡한 프로세스 및 정보 입력 방식을 유지합니다. (기존 인지 부하 수준)
*   **그룹 B (Variant):** **인지 부하 감소를 목표로 설계된 새로운 인터페이스/모듈(예: 초단순 정보 입력 모듈, 최소 마찰 조건 적용)**을 적용합니다.

#### 단계 2: 데이터 수집 및 측정 (Measurement)
각 그룹에 대해 다음 데이터를 수집하고 기록합니다.

1.  **행동 지표 (TTC):** 각 그룹에서 결제 프로세스 완료까지 걸린 평균 시간.
2.  **인지 지표 (PCR):** 세션 중 또는 프로세스 완료 직후 사용자에게 직접 질문하는 설문(예: "이 과정이 얼마나 쉬웠나요? 1-5점")을 통해 수집된 평균 인지 부하 점수.
3.  **비즈니스 지표 (CR):** 각 그룹에서 최종적으로 결제를 완료한 사용자의 비율.

#### 단계 3: 분석 및 정량화 (Analysis & Correlation)
수집된 데이터를 기반으로 **TTC와 PCR의 변화가 CR에 미치는 영향**을 통계적으로 분석합니다.

*   **핵심 분석:** $\Delta (\text{PCR}) \rightarrow \Delta (\text{TTC}) \rightarrow \Delta (\text{CR})$ 의 경로를 검증합니다.
    *   $\text{PCR}$이 감소하면 $\text{TTC}$가 감소해야 하고, $\text{TTC}$의 감소는 $\text{CR}$ 증가로 이어져야 합니다.

### 2. LLM 호출 실패 방지 시스템 설계 (Failure Resilience)

LLM 기반의 자동화된 콘텐츠 생성이나 분석 단계에서 발생하는 실패(API 오류, Context Length 초과, 모델 로드 실패 등)를 최소화하고 복구하는 메커니즘을 도입합니다.

**아키텍처 제안:**
*   **Retry Mechanism (재시도 메커니즘):** API 호출 실패 시 즉시 재시도를 수행하며, 실패 횟수에 따라 지수 백오프(Exponential Backoff) 전략을 적용하여 서버 부하를 관리합니다.
*   **Fallback Strategy (대체 전략):** 주 모델(예: Gemini) 호출이 실패할 경우, 사전에 정의된 대체 모델(예: 다른 LLM 또는 경량화된 모델)로 자동 전환하여 작업을 지속합니다.
*   **Context Management (컨텍스트 관리):** `AI_City_Master_Plan`의 구조를 활용하여, 각 단계별로 필요한 정보만 프롬프트에 주입하고 Context Length 초과를 사전에 모니터링하여 입력 길이를 동적으로 조정합니다.

**통합 계획:**
1.  **데이터 의존성 관리:** LLM이 데이터를 요청할 때, 데이터 파이프라인(Section 1)의 상태를 먼저 확인하도록 로직을 구성합니다. 만약 데이터 수집 단계에서 오류가 발생하면, LLM 호출은 **실패 대신 데이터 불완전 경고**를 반환하고 시스템에 실패 원인을 보고하도록 합니다.
2.  **D2C 계약 반영:** 'Design-to-Code Contract' 내에 **'Error Handling & Fallback Specification'** 섹션을 추가하여, 어떤 종류의 API/LLM 오류가 발생했을 때 시스템이 취해야 할 구체적인 행동(재시도, 대체 모델 사용, 사용자에게 알림)을 명문화합니다.

class DataPipelineError(Exception):
    """데이터 파이프라인 관련 사용자 정의 예외."""
    pass

class LLMFailureError(DataPipelineError):
    """LLM 호출 실패 및 복구 관련 사용자 정의 예외."""
    def __init__(self, message: str, model_name: str, reason: str):
        super().__init__(message)
        self.model_name = model_name
        self.reason = reason

class DataPipeline:
    """
    데이터 수집, 처리 및 A/B 테스트 결과 로깅을 담당하는 핵심 파이프라인 클래스.
    """
    def __init__(self, config: Dict[str, Any]):
        self.config = config
        self.log_history: List[Dict[str, Any]] = []
        logging.info("DataPipeline 초기화 완료.")

    def log_ab_test_result(self, test_id: str, group: str, metric_value: float, llm_status: str, model_used: str, error_reason: str = None):
        """
        A/B 테스트 결과를 데이터 저장소에 기록합니다.
        FTRC 분석 기반의 핵심 KPI를 로깅합니다.
        """
        log_entry = {
            "timestamp": datetime.datetime.now(datetime.timezone.utc).isoformat(),
            "test_id": test_id,
            "group": group,
            "metric_type": "ConversionRate", # MVP Phase 1 핵심 지표
            "value": metric_value,
            "llm_status": llm_status,
            "model_used": model_used,
            "error_reason": error_reason if error_reason else "Success",
            "pipeline_version": self.config.get("pipeline_version", "v1.0")
        }
        self.log_history.append(log_entry)
        logging.info(f"A/B 테스트 결과 로깅: TestID={test_id}, Group={group}, Status={llm_status}")

    def process_data(self, raw_data: List[Dict[str, Any]]) -> List[Dict[str, Any]]:
        """
        실제 데이터 처리 및 품질 레이블링을 수행합니다. (Placeholder)
        여기에 PEI 지수 매핑 로직이 통합될 예정입니다.
        """
        processed_data = []
        for record in raw_data:
            # 실제 PEI 지수 계산 및 레이블링 로직 삽입
            record['quality_label'] = 'OK' # 임시값
            processed_data.append(record)
        logging.info(f"총 {len(raw_data)}건의 데이터를 처리했습니다.")
        return processed_data

def handle_llm_call(model: str, prompt: str, max_retries: int = 3) -> Dict[str, Any]:
    """
    LLM 호출을 시도하고 실패 시 에러를 발생시키며 재시도 로직을 준비합니다.
    실제 LLM API 연동은 추후 구현될 예정입니다.
    """
    for attempt in range(max_retries):
        try:
            # TODO: 실제 LLM API 호출 로직 삽입 (예: Gemini/Veo 호출)
            if "fail" in prompt.lower(): # 시뮬레이션 실패 조건
                raise ValueError("Simulated API Failure due to bad input.")

            result = {"status": "success", "output": f"Processed result from {model} for prompt: {prompt[:30]}..."}
            return result
        except Exception as e:
            logging.warning(f"LLM 호출 실패 (Attempt {attempt + 1}/{max_retries}): {e}")
            if attempt < max_retries - 1:
                # 다음 시도 전에 잠시 대기 (Backoff)
                import time; time.sleep(2 ** attempt)
            else:
                # 최종 실패 시 LLMFailureError 발생
                raise LLMFailureError(f"LLM 호출 최종 실패. 원인: {e}", model_name=model, reason=str(e))

### 1. 기술 사양 및 통합 계획 구체화 (내부 설계)

**목표:** MVP Phase 1 구축을 위한 데이터 로깅, LLM 실패 방지 메커니즘, Design-to-Code Contract의 명확한 통합 정의.

*   **LLM 실패 방지 연동:** LLM 호출 실패 시 자동 재시도 큐(Retry Queue) 메커니즘과 시스템 안정성 지표(Failure Rate)를 연결하여, 사용자 경험 개선 지표(PCR)에 직접적인 영향을 미치도록 정의합니다.
*   **Design-to-Code Contract 통합:** 디자인(UX/KPI) 요구사항이 실제 코드 구현 및 데이터 흐름으로 명확하게 매핑되도록 계약 규칙을 명세화합니다.

### 2. MVP Phase 1 환경 구축을 위한 초기 코드 준비

위의 사양을 기반으로, 데이터 로깅과 시스템 안정성 검증에 필요한 핵심 모듈 파일들을 준비하겠습니다.

## 목표
공인중개사 결제 100건 목표 달성을 위한 MVP Phase 1 환경 구축 및 핵심 지표 검증 시스템 설계.

## 1. 데이터 로깅 아키텍처 (FTRC 연동)
- **입력 계층:** 사용자 입력(정보 모듈) $\rightarrow$ A/B 테스트 그룹 할당 및 초기 입력 데이터 기록.
- **처리 계층:** LLM 호출 요청 $\rightarrow$ 시스템 상태(Latency, Failure Flag) 로깅.
- **출력 계층:** 최종 결과(결제 성공 여부) $\rightarrow$ TTC/PCR 지표 계산 및 저장.
- **핵심 엔티티:** `TestLog`, `LLM_Call_Result`, `KPI_Metric` 테이블 정의.

## 2. LLM 실패 방지 메커니즘 (안정성 확보)
- **가드 시스템:** 모든 외부 API/LLM 호출 전, Context Length 및 메모리 사용량을 사전에 검증하는 가드(Guard) 레이어 구현.
- **재시도 전략:** LLM 실패 시, 설정된 임계값에 따라 자동으로 재시도 큐(Retry Queue)로 이동시키는 로직 정의.
- **안정성 지표:** 시스템 전체의 LLM 실패율을 실시간으로 모니터링하는 메트릭 생성.

## 3. Design-to-Code Contract 통합
- **규칙:** 모든 UI/UX 결정(Designer 산출물 기반)은 데이터베이스 스키마 및 API 엔드포인트 정의에 직접 반영되어야 한다.
- **구현 지침:** React/FastAPI 코드는 이 계약을 따르며, 데이터 흐름의 불일치는 자동 검증 시스템에서 즉시 플래그를 발생시킨다.

## 4. MVP Phase 1 기술 스택 요약
- **Frontend:** React (SPA)
- **Backend:** FastAPI (API Gateway 및 로깅 서비스)
- **AI/ML Layer:** Gemini (LLM 호출), 자체 검증 모듈 (Anti-RAG 통합)
- **Data Layer:** PostgreSQL/Parquet (로깅 데이터 저장)

**다음 단계:** 확정된 사양에 따라, 이 명세를 실제 코드로 구현하기 위한 초기 환경 설정 파일(예: Dockerfile, 초기 DB 스키마 정의)을 준비한다.

**H1:** 사용자 인터페이스(UI)에서 **인지 부하가 감소된 버전**을 경험하는 그룹은 그렇지 않은 그룹보다 **결제 전환율(PCR)**이 통계적으로 유의미하게 높을 것이다.

*   **독립 변수 (Independent Variable):** 정보 입력 모듈의 복잡성 (인지 부하 수준).
    *   **Group A (Control/기존):** 기존의 복잡한 정보 입력 방식을 유지하는 그룹.
    *   **Group B (Variant/실험군):** 인지 부하를 최소화하도록 단순화된 '초단순 정보 입력 모듈'을 경험하는 그룹.
*   **종속 변수 (Dependent Variable):** 결제 전환율(PCR).

### 2. 핵심 측정 지표 (KPIs)

| 지표 구분 | KPI 명칭 | 계산식/정의 | 측정 목적 |
| :--- | :--- | :--- | :--- |
| **주요 성과 지표 (Outcome)** | **결제 전환율 (PCR)** | (성공적인 결제 수) / (총 사용자 수) | 최종 비즈니스 목표 달성 여부 측정. |
| **매개 변수 지표 (Mechanism)** | **인지 부하 점수 (Cognitive Load Score, CLS)** | 입력 단계별 오류율, 체류 시간, 재입력 횟수 등을 종합하여 산출한 정량적 점수 (시스템 내 내부 로그 기반). | 인지 부하 감소가 실제로 발생했는지 측정. |
| **보조 지표 (Guardrail)** | **사용자 이탈률 (Drop-off Rate)** | 특정 단계(정보 입력 또는 결제 직전)에서 이탈한 사용자 비율. | 단순 전환 외에 사용성 및 만족도 저하 여부 방지. |

### 3. 데이터 로깅 방안 (Data Logging Plan)

인지 부하와 PCR 간의 인과관계를 명확히 하기 위해, 시스템 레벨과 사용자 행동 레벨에서 데이터를 동시에 로깅해야 합니다.

1.  **세션/사용자 레벨 로깅:**
    *   **테스트 그룹 할당:** 사용자가 어떤 버전(A 또는 B)을 경험했는지 명확하게 태그합니다.
    *   **결과 기록:** 각 세션 종료 시, **PCR (성공 여부)** 및 **CLS (인지 부하 점수)**를 기록합니다.
2.  **행동 레벨 로깅 (상세):**
    *   **입력 단계별 지연 시간:** 정보 입력 모듈에서 사용자가 특정 필드에 머무르는 평균 시간(TTC - Time To Completion).
    *   **반복 및 수정 횟수:** 사용자가 정보를 수정하거나 재입력한 총 횟수. (이는 인지 부하의 직접적인 측정치로 활용)
3.  **시스템 안정성 로깅:**
    *   **LLM 호출 성공률:** 시스템 안정성(FTRC 목표 준수 여부)을 지속적으로 모니터링하여, PCR 변화가 모델 자체의 불안정성 때문이 아님을 보장합니다.

2.  **검증 지표 (KPI):**
